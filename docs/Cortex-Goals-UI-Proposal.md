# Proposed Cortex support for goals

Status: proposal, 2026-10-25.

Based on [the feature request](../FEATURE-REQUEST-CORTEX-GOALS.md), the current
Cortex UI, and c2j main at `dad7ec835882bbb926bce073d67920fd1754d62b`, which
uses JobDB `86ac74228615`. Implementation should update Cortex to compatible
c2j/JobDB revisions together.

## Recommended experience

**People create goals. Jobs are attempts at goals.** Make this the organizing
principle of the home page and submission flow. Each execution keeps its own
history, reviews, documents, and controls.

Make the home page the jobs list grouped by goal, labelled **Goals** in the
navigation. This is the main working list, not a separate goal dashboard beside
an unrelated flat jobs home. Keep Reviews, Pending Inputs, and Cells available.
Preserve existing job detail URLs; the existing jobs-list route can open the
same grouped view, including its goal and status filters. Goal details remain
independently addressable. Store filters in the URL and preserve them on return.

| Surface | Proposed changes |
| --- | --- |
| Home / Goals | Compact goal headers with job attempts directly underneath, goal and attempt statuses, review links, and **New goal** as the primary action. |
| New goal | One prompt field; submitting creates a goal and its initial job through the existing submission flow. |
| Goal detail | State, winner/result, attempts, a link to filtered reviews, and waiting consumers. |
| Job detail | Identify the job as an attempt at its goal; preserve execution details and goal-aware restart. |
| Reviews | Filter to one goal through a link from that goal; retain each review's own documents and response actions. |

Use the goal ID as the stable identity. c2j v0.0.96 now exposes submission
`prompt` metadata in job listings. Show up to 75 words in the compact row or
group header, falling back to the goal ID when absent. Expanded job details
show the full prompt and other already-loaded listing fields.

## New goal: prompt-only submission

Rename the current **Submit Job / New job** action and dialog to **New goal**.
The form contains one required multiline **Prompt** field and a **Create goal**
button. Remove recipe selection, Job ID entry, and the raw JSON inputs editor.
Use the selected cell context, or the existing default/self target resolution,
without adding another required input to this form. Show the resolved target as
brief context so users know where the work will run.

Submit through the existing c2j recipe-job service. Match `c2j submit` conventions:
put the text in `inputs.prompt`, use the default recipe, and supply the same
implicit default inputs (`inputs.type = "build"` in the reviewed revision).
Use the public default where available and verify CLI parity in integration
coverage. Reject an empty or whitespace-only prompt and preserve entered text
when submission fails. Job and goal identities are generated by the submission
service; users do not choose them.

One submission creates the goal and its initial job. Preserve the returned
`{tenant_id, goal_id, job_id}` and open that goal with its initial attempt
visible. Use **Goal created** for success feedback. There is no additional
create-empty-goal step or change to the underlying execution behavior.

## Home: job attempts grouped by goal

Render one compact header per goal, followed directly by its job rows. Two or
more attempts for the same goal stay together. Each row retains the useful job
status/error information, execution link, selection checkbox, and existing
operations. Use a single grouping level; do not introduce an execution tree
here or hide the only attempt behind an extra click.

The goal header contains its identity/context, authoritative state, a winner
link when applicable, and **View reviews**. Job rows show execution state
separately from the goal state. A failed attempt followed by a successful retry
stays visible under the same goal. Goals without an available attempt still get
a header so open goals needing another attempt remain discoverable.

Query jobs directly with status, cell, and optional goal filters applied on the
server before pagination. Group the returned rows by goal membership in the UI;
the listing does not need `ListGoals` or per-goal candidate queries. A goal link
opens the same jobs view filtered to that goal. Attempts for one goal can span
pages, so displayed group counts describe only the current page. Changing a
filter resets the cursor, and browser history preserves filters and page state.
Authoritative goal state and winner information require separate goal data and
are outside this listing implementation; do not infer them from visible jobs.

Goal membership determines grouping, including additional memberships. A job
that serves several goals can appear in each applicable group with the same job
identity. Bulk selection is deduplicated by job ID so an operation is submitted
once per job.

## Goal details: result first, executions underneath

The header shows the authoritative **Open**, **Succeeded**, or **Failed** state.
A succeeded goal links to its committed winner. A failed goal shows its recorded
reason, time, and candidate snapshots at failure time, separately from current
candidate statuses. Unavailable job details must not erase these facts.

For open goals, display useful explanations without inventing extra goal states:

- **Needs another attempt** when there are no unfinished candidates and none
  are unavailable.
- **No known unfinished candidates** when unavailable candidates prevent a
  stronger conclusion.
- **Review available** when a related pending review has actually been found.

Label nonterminal counts **Unfinished**, not **Running**: ready, blocked, and
waiting jobs are included. Counts come from the goal summary and cover the whole
goal, even when repository or cell filters select it through one candidate.

Use two tabs: **Attempts** and **Waiting consumers**, plus a **View reviews** link
that opens the existing Reviews page filtered to this goal. With just one
candidate, make its job and available review directly accessible. With multiple
candidates, retain the table without designating the newest as the current one.

The Attempts table shows execution status and completion detail, repository/recipe,
primary or additional membership, winner marker, and restart relationship where
the API provides it. It includes all job types and retained archived/hidden
candidates through server pagination. Unsupported or unavailable job details get
an explicit explanation instead of a broken recipe-specific view.

Goal actions include **Attach existing job** and **Fail goal**. Attaching an
already successful job can immediately satisfy an open goal; explain that before
confirmation. Failing requires a reason and confirmation that failure is
permanent and does not cancel candidates. Cancellation and deletion continue to
target explicit jobs, always with confirmation.

## Jobs for a specific goal

Provide **View attempts** from goal details, opening the grouped home list
filtered to that goal. Use the existing goal-ID filter in c2j/JobDB, including primary and
additional memberships. Show all statuses by default and let users narrow the
list with the existing status filters. Preserve the goal filter in the URL and
when returning from a job detail page.

For five approaches to one goal, this gives the user one list of those jobs,
their statuses, and links to their execution details. After one succeeds, the
user can select remaining jobs and use the existing confirmed bulk Cancel or
Delete operations. Cancellation remains a manual choice.

Keep the requested small icon for unfinished jobs whose goal is already met,
with an accessible description and tooltip rather than a large label. Use
existing goal reads for that information. Additional memberships remain visible
so users can see whether a job also serves another goal.

This uses existing APIs. No cross-goal goal-state filter or upstream enhancement
is needed for the proposed flow.

## Reviews: filter to one goal

Add a goal filter to the existing Reviews page and link to it from goal details.
The filtered list includes reviews from any number of associated candidates,
using backend pagination. Preserve the selected goal in the URL and when
returning from an individual review. Include job links, review titles, and
document counts; keep request IDs as submission identity rather than adding
prominent technical labels.

Open each review in the existing detail view with its document selector,
rendered Markdown/source toggle, and recipe-defined response form. Documents
remain immutable. There is no paired comparison view or limit of two candidates.

Submitting a response acts only on that review's exact job and request. Preserve
recipe-provided decisions rather than inventing a universal “approve” value.
Refresh stale review data and handle goal closure races explicitly. For a met
goal, offer confirmed cancellation of that review's job alongside the existing
response actions and explain that it cannot replace the recorded winner.

**Review approval is not winner selection.** Under the current contract, the
first candidate whose success JobDB commits wins. Allowing one review to proceed
does not reserve the goal or prevent a different candidate from succeeding.
The user can manually cancel other jobs through the existing controls.

Association must come from structured goal membership. Direct candidate reviews
can be discovered through paginated c2j job queries by goal ID and input task,
then loaded through the public input/review service. Preserve continuation even
when a page contains ordinary inputs but no reviews. Do not scan every job's
story to find reviews.

A review owned by a child job is not automatically a candidate review for every
goal of its parent. Include descendant reviews only when the public contract
provides an explicit association, and show both the candidate and owning job.
If recipes rely on that arrangement, verify it with a representative recipe and
request a public association/query API where needed, rather than interpreting
agent text or invocation IDs.

## Restart, submission, and waiting jobs

Keep the restart button tied to the clicked execution boundary. Use c2j's
recorded `restart_scope_id` for context inspection and submission; compact
chapters can contain several boundaries. Keep the full before/after context
preview and patch controls.

Offer **Continue this goal** as the default for a new restart of an open primary
goal, and **Start a new goal** for independent work. A succeeded or explicitly
failed goal cannot be continued; require the new-goal choice for a fresh attempt.
If the goal closes during submission, show the conflict without silently
changing modes. Continuation does not cancel existing jobs or inherit additional
goal memberships.

Persist the request ID and exact payload together before sending. An unresolved
submission survives reload and offers reconciliation with the same request,
even if its accepted candidate has since won and closed the goal. A genuinely
new attempt gets a new ID. Preserve the native `{tenant_id, goal_id, job_id}`
response end to end, then navigate to the new job with a clear goal link. Use
the existing UUID helper that works on plain HTTP.

Distinguish **working toward a goal** (candidate membership) from **waiting for
a goal** (dependency). Long-lived coordinator jobs can remain waiting while
candidate executions fail, restart, or succeed. Show **Waiting for goal G** when
the structured blocking wait says that; do not label ordinary idle or input
waits as goal waits. The UI should not imply that restarting a candidate is how
every coordinator receives its next assignment.

The Waiting consumers tab lists currently unresolved reverse dependencies.
The consumer's job detail shows its complete recorded wait, conditions,
deadlines, failures, and result bindings, including retained historical waits.
Use the recorded wait ID. Preserve the distinction between the originally
submitted job, the waited-on goal, and the actual producer of the result.
For example, A fails, B continues G and wins, and parent P receives B's result:
all four facts remain visible.

A reverse edge disappearing does not prove the consumer completed: another
dependency may still block it, or its deadline may have elapsed. Present the
API's projected timeout state without writing anything during reads.

## API integration and refresh

Use c2j's public goal, candidate, lifecycle, and dependency-wait services. Add
typed Cortex goal-query and dependency-wait-query endpoints, along with goal
detail, candidate pagination/attachment, and failure endpoints. Keep the route's
project/tenant authoritative and lifecycle permissions separate from task
submission permissions. Goal-filtered review discovery can be a bounded Cortex
composition of public services; avoid duplicating scheduler semantics.

Use real server pagination for goals, candidates, filtered jobs, and waits.
Preserve opaque cursors, reset them when tenant or filters change, and ignore
responses from a previous selection. Pages are live views, not snapshots with
guaranteed stable totals. Batch enrichment of visible jobs must not be mistaken
for tenant-wide discovery.

Refresh visible candidate counts, candidate rows, reviews, and wait data even
when the goal revision is unchanged: candidate activity does not necessarily
change that revision. Succeeded goals can still have active candidates. Honor
the user's auto-refresh setting across all reloads and provide manual refresh.

## Delivery and verification

Implement in three increments:

1. Update compatible dependencies and native reference types; implement goal
   and wait read APIs, restart modes, recorded scopes, and durable submission
   reconciliation.
2. Make the grouped jobs list the Goals home, replace submission with the
   prompt-only New goal flow, and add goal details, candidate and consumer views,
   goal filters, and small met-goal icons.
3. Add goal-filtered review discovery and navigation, goal lifecycle actions,
   and the complete browser workflows below.

Follow the requested clean cutover: retire old workers/submitters and remove old
jobs through a separately scheduled deployment operation. No legacy adapters,
backfills, or reconstruction of goals from old histories are proposed.

Browser and API acceptance coverage should include:

- Create a goal with only a prompt: recipe and Job ID controls and raw JSON are
  absent; default target/recipe and input structure match `c2j submit`; the
  returned goal and initial job are shown together. Blank input is rejected,
  and a failed submission preserves the prompt.
- Home groups several attempts at the same goal together, including failure
  followed by restart. Goal and candidate pagination keep groups coherent;
  a job with additional memberships is acted on only once during bulk actions.
- One candidate and one review: render/source documents, response submission,
  direct job navigation, and goal outcome.
- Five candidates: follow the goal's reviews link, browse all matching reviews
  across pages, open one and let it proceed, then return with the filter intact.
  Commit its success, follow the goal's attempts link, narrow by existing status
  filters, verify the small icons and tooltips, and confirm bulk cancellation. Include
  an additional open goal on one selected job and a per-job cancellation failure.
- Failed A, continued B, and waiting P: B wins G and P displays B's recorded
  producer binding while A retains its failure.
- Lost restart response followed by reload and reconciliation after goal
  success: exactly one new candidate, correct scope, context patch, and IDs.
- Open goals without candidates, authoritative counts across page boundaries,
  unchanged goal revisions with changing counts, hidden/unavailable candidates,
  and explicit failure snapshots distinct from live candidate state.
- Listing jobs for a specific goal across multiple backend pages, including
  primary and additional memberships without duplicates. Preserve goal and
  status filters when returning from details.
- Multi-target waits, reverse-edge removal, elapsed deadlines, and historical
  waits inspected through the consumer.
- Tenant isolation, stale responses after filter changes, plain-HTTP UUID
  generation, immutable review documents, and auto-refresh remaining disabled
  after the user turns it off.
