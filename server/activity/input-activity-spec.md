# Input Activity Specification

## Overview
Input Activities are interactive activities that pause workflow execution to gather user responses through the Cortex server (vibethis core server). These activities use a Google Forms-compatible model to present multiple questions in a single form, supporting standard field types for consistent user experience. The activity server communicates with Cortex via signals to coordinate user interactions and manage workflow state.

## Core Components

### Activity Type - Input Form

Input activities follow the Google Forms model. The common case of a single question is made simple, while still supporting multiple questions when needed.

#### Simple Single Question Format

```yaml
# Minimal config for common case
type: input
config:
  question: "Do you approve this deployment?"
  type: "multiple_choice"
  options:
    - value: "approve"  # Label defaults to "approve"
    - value: "reject"   # Label defaults to "reject"
```

```yaml
# With custom labels when needed
type: input
config:
  question: "Select environment"
  type: "multiple_choice"
  options:
    - value: "prod"
      label: "Production Environment"  # Optional custom label
    - value: "staging"  # Uses "staging" as label
    - value: "dev"      # Uses "dev" as label
```

```yaml
# Single question with artifacts
type: input
config:
  question: "Please review the configuration and provide feedback"
  type: "paragraph_text"
  context:
    artifacts_glob:
      - pattern: "generated/*.yaml"
```

##### Input Resolution at Runtime
```yaml
type: input
config:
  title: "Review Scan Results"
  context:
    # Artifacts resolved at runtime from multiple sources (automatically deduplicated)
    artifacts_resolution:
      sources:
        - type: "activity_output"
          activity: "code_generator"
          field: "generated_files"
        - type: "glob"
          patterns: ["temp/*.tmp", "cache/*.json"]
        - type: "directory"
          path: "output/latest/"
          recursive: true
          filter: "*.yaml"
```

#### Artifact Resolution Methods

1. **Static Paths** - Hardcoded file paths
   ```yaml
   artifacts:
     - path: "config.yaml"
   ```

2. **Activity Output Reference** - Files from previous activity
   ```yaml
   artifacts_from_output: "previous_activity.output_field"
   ```

3. **Glob Patterns** - Pattern matching
   ```yaml
   artifacts_glob:
     - pattern: "**/*.yaml"
       exclude: ["**/test/**", "**/backup/**"]
   ```

4. **Directory Listing** - All files in directory
   ```yaml
   artifacts_directory:
     path: "output/"
     recursive: true
     extensions: [".json", ".yaml"]
   ```

5. **Combined Resolution** - Multiple sources with automatic deduplication
   ```yaml
   artifacts_resolution:
     sources: [...]
   ```

### Response Data Access

Responses are accessed using the standard recipe templating mechanism:

#### Single Question Response
```yaml
steps:
  - name: approval_check
    type: input
    config:
      question: "Do you approve this deployment?"
      type: "multiple_choice"
      options:
        - value: "approve"
        - value: "reject"
  
  - name: deploy
    type: deployment
    config:
      # Access using standard template syntax
      proceed: "{{ .Steps.approval_check.outputs.response }}"

# Output structure for single question:
# .Steps.approval_check.outputs:
#   response: "approve"

#     responded_by: "user_123"
```

#### Option Label Behavior

When defining options for multiple_choice, checkboxes, or dropdown fields:
- **Labels are optional** - If not specified, the value is used as the display text
- **Values should be machine-readable** - Use lowercase, underscores, no spaces
- **Labels are for display** - Human-readable text shown to users

```yaml
# Simple case - values used as labels
options:
  - value: "yes"
  - value: "no"
  - value: "maybe"

# Mixed - some with custom labels
options:
  - value: "prod"
    label: "Production Environment"
  - value: "staging"  # Shows as "staging"
  - value: "dev"      # Shows as "dev"
```

#### Supported Field Types (Google Forms Compatible)

1. **short_answer** - Single line text input
   ```yaml
   type: "short_answer"
   validation:
     max_length: 100
     pattern: "^[A-Za-z0-9_-]+$"  # Optional regex
   ```

2. **paragraph_text** - Multi-line text input
   ```yaml
   type: "paragraph_text"
   validation:
     max_length: 1000
   ```

3. **multiple_choice** - Single selection from options
   ```yaml
   type: "multiple_choice"
   options:
     - value: "opt1"  # Label defaults to "opt1"
     - value: "opt2"
       label: "Custom Label"  # Optional custom label
   allow_other: true  # Optional "Other" field
   ```

4. **checkboxes** - Multiple selections
   ```yaml
   type: "checkboxes"
   options:
     - value: "opt1"  # Label defaults to "opt1"
     - value: "opt2"
       label: "Custom Label"  # Optional
   validation:
     min_selections: 1
     max_selections: 3
   ```

5. **dropdown** - Dropdown selection
   ```yaml
   type: "dropdown"
   options:
     - value: "opt1"  # Label defaults to "opt1"
     - value: "opt2"
       label: "Custom Label"  # Optional
   ```

6. **linear_scale** - Numeric scale rating
   ```yaml
   type: "linear_scale"
   scale:
     min: 1
     max: 10
     min_label: "Strongly Disagree"
     max_label: "Strongly Agree"
   ```

7. **multiple_choice_grid** - Grid of multiple choice questions
   ```yaml
   type: "multiple_choice_grid"
   rows:
     - "Feature A"
     - "Feature B"
   columns:
     - "Essential"
     - "Nice to have"
     - "Not needed"
   ```

8. **checkbox_grid** - Grid of checkbox questions
   ```yaml
   type: "checkbox_grid"
   rows:
     - "Region US"
     - "Region EU"
   columns:
     - "Deploy"
     - "Monitor"
     - "Rollback"
   ```

9. **date** - Date picker
   ```yaml
   type: "date"
   validation:
     min_date: "2024-01-01"
     max_date: "2024-12-31"
   ```

10. **time** - Time picker
    ```yaml
    type: "time"
    validation:
      min_time: "09:00"
      max_time: "17:00"
    ```

11. **file_upload** - File attachment (reference to artifacts)
    ```yaml
    type: "file_upload"
    accept: ".yaml,.json"
    max_files: 3
    ```

## Implementation Structure

### Activity Handler
```go
// server/activity/pkg/activity/input.go
type InputActivity struct {
    Type           string
    CortexClient   *cortex.Client
    ResponseStore  ResponseStore
}

type InputForm struct {
    // Simple single question format
    Question       string      // For single question forms
    Type           FieldType   // Field type for single question
    Options        []Option    // Options for single question
    
    // Multi-field format
    Title          string      // Optional title for multi-field forms
    Fields         []FormField // For multiple questions
    
    // Common fields
    Context        FormContext
    Timeout        int
}

type FormContext struct {
    // Static artifacts
    Artifacts      []Artifact
    
    // Dynamic artifact resolution
    ArtifactsFromOutput string           // Reference to previous activity output
    ArtifactsGlob      []GlobPattern     // Glob patterns to match files
    ArtifactsDirectory *DirectoryListing // Directory to list
    ArtifactsResolution *ArtifactResolution // Advanced resolution config
}

type ArtifactResolution struct {
    Sources        []ArtifactSource
    // Deduplication happens automatically
}

type ArtifactSource struct {
    Type           string  // "activity_output", "glob", "directory", "static"
    ActivityRef    string  // For activity_output type
    OutputField    string  // For activity_output type
    Patterns       []string // For glob type
    Path           string  // For directory type
    Recursive      bool    // For directory type
}

type FormField struct {
    ID             string
    Type           FieldType  // Matches Google Forms types
    Question       string
    Required       bool
    Placeholder    string
    Options        []Option
    Validation     FieldValidation
    DependsOn      *FieldDependency  // Conditional logic
    GenerateFromArtifacts bool  // For dynamic_grid type
}

type Option struct {
    Value string
    Label string  // Optional - defaults to Value if not specified
}

type FieldType string

const (
    ShortAnswer       FieldType = "short_answer"
    ParagraphText     FieldType = "paragraph_text"
    MultipleChoice    FieldType = "multiple_choice"
    Checkboxes        FieldType = "checkboxes"
    Dropdown          FieldType = "dropdown"
    LinearScale       FieldType = "linear_scale"
    MultipleChoiceGrid FieldType = "multiple_choice_grid"
    CheckboxGrid      FieldType = "checkbox_grid"
    Date              FieldType = "date"
    Time              FieldType = "time"
    FileUpload        FieldType = "file_upload"
)

type FormResponse struct {
    ActivityID     string
    UserID         string
    
    // For single question forms
    Response       interface{}  // Direct response value
    
    // For multi-field forms  
    Fields         map[string]interface{}  // field_id -> response value
    
    // Metadata
    SubmittedAt    time.Time
    TimeToComplete int  // seconds
}

type UserResponse struct {
    ActivityID     string
    UserID         string
    Response       interface{}
    Timestamp      time.Time
    Justification  string
}
```

## Signal-based Communication Architecture

Input activities use signals for all communication between the Activity server and Cortex. This provides asynchronous, event-driven coordination that naturally fits with workflow pause/resume patterns.

### Signal Definitions

#### Activity → Cortex Signals
```go
// InputRequested - Activity requests user input form
type InputRequested struct {
    ActivityID     string
    WorkflowID     string
    Form          InputForm
    Context       map[string]interface{}
    Timeout       time.Duration
}

// InputCancelled - Activity cancels pending input
type InputCancelled struct {
    ActivityID string
    ResponseID string
    Reason     string
}
```

#### Cortex → Activity Signals
```go
// InputReady - Cortex has prepared the user input session
type InputReady struct {
    ActivityID  string
    ResponseID  string
    SessionID   string
    DisplayURL  string
    ExpiresAt   time.Time
}

// InputReceived - User has submitted form
type InputReceived struct {
    ActivityID    string
    ResponseID    string
    FormResponse  FormResponse  // All field responses
    UserID        string
    RespondedAt   time.Time
}

// InputTimeout - Input request has timed out
type InputTimeout struct {
    ActivityID string
    ResponseID string
    TimedOutAt time.Time
}

// InputError - Error processing user input
type InputError struct {
    ActivityID string
    ResponseID string
    Error      string
    ErrorCode  string
}
```

### Signal Flow
1. Activity sends `InputRequested` signal to Cortex
2. Cortex responds with `InputReady` signal containing session info
3. Activity enters wait state, listening for response signals
4. When user responds, Cortex sends `InputReceived` signal
5. Activity processes response and continues workflow

### Signal Implementation Details

#### Signal Handler Registration
```go
// server/activity/pkg/activity/input_handler.go
func RegisterInputHandlers(dispatcher *signals.Dispatcher) {
    dispatcher.RegisterHandler("InputReady", HandleInputReady)
    dispatcher.RegisterHandler("InputReceived", HandleInputReceived)
    dispatcher.RegisterHandler("InputTimeout", HandleInputTimeout)
    dispatcher.RegisterHandler("InputError", HandleInputError)

func HandleInputReceived(ctx context.Context, signal InputReceived) error {
    // Resume activity with user response
    activity := GetActivity(signal.ActivityID)
    return activity.Resume(signal.Response, signal.Justification)
}
```

### Cortex Server Integration
```go
// server/cortex/pkg/activity/input.go
type InputManager struct {
    Store         InputStore
    Notifier      UserNotifier
    SignalClient  signals.Client
    SignalHandler signals.Handler
}

// Initialize signal handlers on Cortex side
func (m *InputManager) RegisterHandlers() {
    m.SignalHandler.Register("InputRequested", m.HandleInputRequest)
    m.SignalHandler.Register("InputCancelled", m.HandleInputCancelled)
}

func (m *InputManager) HandleInputRequest(ctx context.Context, signal signals.Signal) error {
    req := signal.Payload.(InputRequested)
    
    // Store request with metadata
    session := m.Store.CreateSession(SessionConfig{
        ActivityID:     req.ActivityID,
        WorkflowID:     req.WorkflowID,
        Type:          req.Type,
        Prompt:        req.Prompt,
        Context:       req.Context,
        ResponseSchema: req.ResponseSchema,
        Timeout:       req.Timeout,
    })
    
    // Notify user through available channels
    m.Notifier.NotifyPendingInput(session)
    
    // Send ready signal back to activity
    return m.SignalClient.Send(ctx, signals.Signal{
        Type: "InputReady",
        Payload: InputReady{
            ActivityID:  req.ActivityID,
            ResponseID:  session.ResponseID,
            SessionID:   session.ID,
            DisplayURL:  m.generateDisplayURL(session),
            ExpiresAt:   session.ExpiresAt,
        },
    })
}

// Called when user submits response through UI
func (m *InputManager) ProcessUserResponse(ctx context.Context, responseID string, response UserResponse) error {
    session := m.Store.GetSessionByResponseID(responseID)
    if session == nil {
        return fmt.Errorf("session not found")
    }
    
    // Validate response against schema
    if err := m.validateResponse(response, session.ResponseSchema); err != nil {
        return err
    }
    
    // Send response signal to activity
    return m.SignalClient.Send(ctx, signals.Signal{
        Type: "InputReceived",
        Payload: InputReceived{
            ActivityID:    session.ActivityID,
            ResponseID:    responseID,
            Response:      response.Value,
            Justification: response.Justification,
            UserID:        response.UserID,
            RespondedAt:   time.Now(),
        },
    })
}
```

### Activity Server Integration
```go
// server/activity/pkg/activity/input_activity.go
type InputActivity struct {
    SignalClient  signals.Client
    SignalWaiter  signals.Waiter
    Config        InputConfig
}

func (a *InputActivity) Execute(ctx context.Context, input ActivityInput) (ActivityOutput, error) {
    // Resolve artifacts dynamically
    artifacts, err := a.resolveArtifacts(ctx, input)
    if err != nil {
        return nil, fmt.Errorf("failed to resolve artifacts: %w", err)
    }
    
    // Prepare form with resolved artifacts
    form := a.Config.Form
    form.Context.Artifacts = artifacts
    
    // Generate dynamic fields if needed
    if a.Config.GenerateDynamicFields {
        form.Fields = a.generateFieldsFromArtifacts(artifacts, form.Fields)
    }
    
    // Send signal to Cortex requesting user input
    requestSignal := signals.Signal{
        Type: "InputRequested",
        Payload: InputRequested{
            ActivityID:     a.ID,
            WorkflowID:     a.WorkflowID,
            Form:          form,
            Context:       map[string]interface{}{
                "artifacts": artifacts,
                "previous_outputs": input.PreviousOutputs,
            },
            Timeout:       a.Config.Timeout,
        },
    }
    
func (a *InputActivity) resolveArtifacts(ctx context.Context, input ActivityInput) ([]Artifact, error) {
    var artifacts []Artifact
    
    // Get artifacts from previous activity output
    if ref := a.Config.Form.Context.ArtifactsFromOutput; ref != "" {
        parts := strings.Split(ref, ".")
        if len(parts) == 2 {
            if output, ok := input.PreviousOutputs[parts[0]]; ok {
                if files, ok := output[parts[1]].([]string); ok {
                    for _, file := range files {
                        artifacts = append(artifacts, Artifact{
                            Path: file,
                        })
                    }
                }
            }
        }
    }
    
    // Apply glob patterns
    for _, glob := range a.Config.Form.Context.ArtifactsGlob {
        matches, _ := filepath.Glob(glob.Pattern)
        for _, match := range matches {
            artifacts = append(artifacts, Artifact{
                Path: match,
            })
        }
    }
    
    // Always deduplicate artifacts
    artifacts = deduplicateArtifacts(artifacts)
    
    return artifacts, nil
}
    
    if err := a.SignalClient.Send(ctx, requestSignal); err != nil {
        return nil, fmt.Errorf("failed to request user input: %w", err)
    }
    
    // Wait for response signal
    responseSignal, err := a.SignalWaiter.WaitFor(ctx, []string{
        "InputReceived",
        "InputTimeout",
        "InputError",
    }, a.Config.Timeout)
    
    if err != nil {
        return nil, fmt.Errorf("failed waiting for user response: %w", err)
    }
    
    // Handle response based on signal type
    switch responseSignal.Type {
    case "InputReceived":
        received := responseSignal.Payload.(InputReceived)
        return ActivityOutput{
            "response": received.Response,
            "justification": received.Justification,
            "user_id": received.UserID,
        }, nil
        
    case "InputTimeout":
        if a.Config.DefaultOnTimeout != nil {
            return ActivityOutput{"response": a.Config.DefaultOnTimeout}, nil
        }
        return nil, fmt.Errorf("user input timeout")
        
    case "InputError":
        errorPayload := responseSignal.Payload.(InputError)
        return nil, fmt.Errorf("user input error: %s", errorPayload.Error)
        
    default:
        return nil, fmt.Errorf("unexpected signal type: %s", responseSignal.Type)
    }
}
```

## Workflow Integration

### Execution Flow
1. Activity executor encounters user input activity
2. Activity sends `InputRequested` signal to Cortex
3. Cortex prepares user session and sends `InputReady` signal back
4. Activity enters wait state, listening for response signals
5. User receives notification and accesses Cortex UI
6. User submits response through Cortex UI
7. Cortex validates response and sends `InputReceived` signal
8. Activity receives signal and resumes with user response as output

#### SSE Connection Management
```typescript
// Single SSE connection for all user inputs across all boxes
class InputStreamManager {
  private eventSource: EventSource;
  private reconnectTimeout: number = 5000;
  
  connect() {
    this.eventSource = new EventSource('/api/user-inputs/stream', {
      withCredentials: true
    });
    
    this.eventSource.addEventListener('initial', (e) => {
      const data = JSON.parse(e.data);
      this.handleInitialLoad(data.pending_inputs);
    });
    
    this.eventSource.addEventListener('input_requested', (e) => {
      const input = JSON.parse(e.data);
      this.notifyNewInput(input);
    });
    
    this.eventSource.addEventListener('input_completed', (e) => {
      const data = JSON.parse(e.data);
      this.removeInput(data.response_id);
    });
    
    this.eventSource.addEventListener('input_expired', (e) => {
      const data = JSON.parse(e.data);
      this.handleExpired(data.response_id);
    });
    
    this.eventSource.onerror = () => {
      this.reconnect();
    };
  }
  
  private reconnect() {
    setTimeout(() => this.connect(), this.reconnectTimeout);
  }
}
```

### Signal Flow with UI

1. Activity sends `InputRequested` signal to Cortex
2. Cortex stores request and sends `InputReady` signal back to activity
3. Cortex pushes SSE event to all connected UI clients for that user
4. UI receives event and updates notification badge/counter
5. User clicks notification to see all pending inputs
6. UI fetches full details for selected input via REST API
7. User submits response through UI
8. Cortex sends `InputReceived` signal to activity
9. Cortex pushes SSE event to update all UI clients
10. Activity resumes with user response

### Connection and Performance Considerations

#### SSE Connection Management
- Single persistent connection per user session
- Automatic reconnection with exponential backoff
- Heartbeat events every 30 seconds to detect stale connections
- Initial event sends all pending inputs on connection

#### Scalability
- SSE connection handled by dedicated streaming service
- Redis pub/sub for distributing events across server instances
- Connection limit per user (prevent multiple tabs from overwhelming)
- Graceful degradation to polling if SSE unavailable

### Cortex Server SSE Implementation
```go
// server/cortex/pkg/api/input_stream.go
type InputStreamer struct {
    Store        InputStore
    PubSub       pubsub.Client
    Connections  map[string]*SSEConnection
}

func (s *InputStreamer) HandleStream(w http.ResponseWriter, r *http.Request) {
    userID := getUserFromContext(r.Context())
    
    // Set SSE headers
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    
    // Create SSE connection
    conn := &SSEConnection{
        Writer:  w,
        Flusher: w.(http.Flusher),
        UserID:  userID,
    }
    
    // Send initial state
    pending := s.Store.GetPendingForUser(userID)
    conn.SendEvent("initial", map[string]interface{}{
        "pending_inputs": pending,
    })
    
    // Subscribe to updates
    sub := s.PubSub.Subscribe(fmt.Sprintf("user:%s:inputs", userID))
    defer sub.Close()
    
    // Handle events
    for {
        select {
        case msg := <-sub.Channel():
            conn.SendEvent(msg.Type, msg.Data)
        case <-r.Context().Done():
            return
        case <-time.After(30 * time.Second):
            conn.SendEvent("heartbeat", map[string]interface{}{
                "timestamp": time.Now(),
            })
        }
    }
}

// Triggered when new user input is created
func (s *InputStreamer) NotifyInputRequested(input Input) {
    s.PubSub.Publish(
        fmt.Sprintf("user:%s:inputs", input.UserID),
        Message{
            Type: "input_requested",
            Data: input.ToSummary(),
        },
    )
}
```

## Error Handling

### Timeout Behavior
- Configurable timeout per activity via signal metadata
- Default timeout: 5 minutes
- On timeout: Cortex sends `InputTimeout` signal
- Activity can handle timeout signal to fail, retry, or use default

### Signal Failures
- Automatic retry with exponential backoff (configured in signal broker)
- Dead letter queue for persistent failures
- `InputError` signal sent for non-recoverable errors
- Activity receives error signal and decides how to proceed

## Security Considerations

1. **Response Validation**: All user responses validated against schema
2. **Context Sanitization**: Sensitive data removed before Cortex calls
3. **Rate Limiting**: Per-user rate limits on response submissions
4. **Audit Trail**: All user inputs logged with timestamp and user ID
