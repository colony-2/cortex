# DeprecationRecipe Specification

## Overview
DeprecationRecipe consumes a `DeprecationPlan` generated by TicketRecipe and orchestrates staged enforcement until deprecated patterns are eliminated across affected cells. It is launched asynchronously, operates in a discrete gitstate, and relies on repeated detection/cleanup/merge loops powered by fast-forward merges (via `squashrebasemerge` with `skip_rebase`).

## Goals
- Identify all consumers of the deprecated API on the current `main` branch using command-line detection tooling.
- Spawn child TicketRecipes (in parallel) to remediate each consuming cell.
- After dependents are clean, remove the deprecated API in the owner cell, verify no usages remain, and fast-forward merge the cleanup onto `main`.
- Provide deterministic recovery when `main` advances or new usages appear between attempts.

## DeprecationPlan Format
Stored at `.colony2/deprecations/{ticket_id}.json` and attached to the ticket record:

```json
{
  "ticket_id": "tkt_123",
  "generated_at": "2025-10-08T21:55:00Z",
  "steps": [
    {
      "id": "deprecated-config-flag",
      "summary": "Remove use of config flag X in adapters",
      "detection": {
        "command": "rg --files-with-matches 'ConfigFlagX' src/adapters",
        "working_dir": "{{cellRoot}}"
      },
      "targets": ["ui-app", "ui-flowchart"],
      "owner_cell": "core-platform"
    }
  ]
}
```

Fields:
- `id`: Stable identifier for cross-referencing.
- `summary`: Instruction provided to downstream tickets.
- `detection`: Shell command executed against repositories to confirm the pattern is gone; run via `command_execution`.
- `targets`: Initial list of cells expected to need remediation (final list comes from detection output).
- `owner_cell`: Cell responsible for owning/removing the deprecated API.

## Inputs
- `ticket_id`
- `plan_uri` (path or blob reference)
- `owner_cell`

## Outputs
- `completed_steps` (array of step ids)
- `remaining_steps`
- `final_report` (markdown summary)

## Assumptions
- DeprecationPlan stored at `.colony2/deprecations/{ticket_id}.json`.
- Detection commands run via `command_execution` with `check_conditions`, emitting machine-readable cell lists via standard CLI tooling (`rg`, `jq`, `moon query projects --json`, etc.).
- `squashrebasemerge` op supports `skip_rebase: true` (see git fast-forward spec).

## State Machine
```
LoadPlan -> StepPreparation -> FanOutTickets -> MonitorProgress -> OwnerCleanup -> DetectionAndMerge -> StepCompletion -> Finalize
```

### LoadPlan
- Fetch plan JSON, validate schema, ensure owner ticket remains completed.
- Initialise progress tracker persisted in recipe payload to support retries.

### StepPreparation
- Determine outstanding target cells (skip those already marked complete) by running the step detection command in a pristine `main` checkout using `command_execution` with `check_conditions`. Pipe results through CLI helpers (e.g., `rg`, `awk`, `jq`, `moon query projects --json`) to emit a normalized JSON array or newline list of impacted cell slugs.
- Capture latest `main` hash for reference notes.

### FanOutTickets
- Feed the normalized detection output into a `recipe_set` op so child TicketRecipes run in parallel (each child configured with discrete gitstate).
- For each entry, invoke the ticket recipe with requirements derived from the step summary (detection command, expected new behaviour, tests to run).
- Track async handles for later monitoring.

### MonitorProgress
- Wait for all child tickets to complete. On failure, post summary to parent ticket via `ticket.manage` and request human input (`input` op) before retrying or skipping.
- Once all children succeed, run `thinpackrebase` in the DeprecationRecipe workspace to pull their changes into the owner cell view (this resets the owner branch onto the latest `main`).

### OwnerCleanup
- Within the owner cell workspace (post-thinpackrebase), remove or adjust the deprecated API itself (e.g., delete methods/types). Use `codex.exec` or scripted modifications.
- Run owner cell tests (plan-provided commands).

### DetectionAndMerge
- Fetch/pristine checkout of remote `main` within the discrete workspace (ensure `thinpackrebase` brought latest main).
- Execute detection command against the owner workspace to confirm deprecated patterns are gone.
  - If detection finds matches **in owner cell** (i.e., code removal incomplete), return to OwnerCleanup.
- Execute detection against current remote `main` (without owner changes). If matches exist, identify affected modules (via detection output) and enqueue new child TicketRecipes for those cells, then:
  - Wait for their completion (using MonitorProgress logic).
  - Run `thinpackrebase` again to incorporate their changes and loop back through OwnerCleanup.
- When detection passes on both owner workspace and remote `main`:
  - Run designated test suite (e.g., `moon test --affected`).
  - Execute `squashrebasemerge` with `skip_rebase: true` to fast-forward merge the owner branch.
  - If the op returns `NotFastForward` (main advanced), run `thinpackrebase` to replay the owner branch on top of the new `main`, rerun detection to identify new consumers, enqueue tickets as needed, and loop back through MonitorProgress → OwnerCleanup.

### StepCompletion
- Record note via `ticket.manage` summarizing detection results, child tickets spawned, merge commit hash, and retry history.
- Mark step as completed in recipe state and advance pointer.

### Finalize
- Generate final report via `llm_inference2` summarizing overall deprecation effort (child tickets, detection attempts, merges).
- Emit event `deprecation.completed`.

## Error Handling
- Child ticket failure: escalate via `input`, optionally requeue after remediation.
- Detection command error (non-zero exit unrelated to matches): capture logs, retry with backoff, escalate if persistent.
- Tests failing during fast-forward: treat as detection failure—open/remediate via child ticket and repeat flow.
- Fast-forward repeatedly failing: after N cycles, mark recipe `blocked` with reason `main_out_of_date` and await manual intervention.

## Observability
- Temporal search attributes: `deprecation_ticket_id`, `current_step`, `status` (`waiting_children`, `cleanup`, `detection`, `merge_retry`).
- Metrics: `deprecation_detection_attempts`, `deprecation_detection_failures`, `deprecation_ff_merge_retries`, `deprecation_child_tickets_spawned`.
- Structured logs spanning child ticket IDs, detection outputs, thinpackrebase results, and fast-forward merges.

## Implementation Notes
- Operate in discrete gitstate to avoid polluting developer workspaces; run thinpack after every successful child wave.
- Ensure steps are idempotent (persist list of spawned child tickets, detection statuses) so recipe can resume on restart.
- Provide configuration for detection/test timeouts, max FF retries, and owner cleanup commands (LLM vs. scripted).

## Open Questions
- How to prioritize child ticket creation when new modules appear (batch vs. single ticket per detection output)?
- Should owner cleanup rely exclusively on `codex.exec` or support manual patches (command execution)?
- Do we expose detection/test logs as attached markdown or reference stored blobs?
