# TicketRecipe Specification

## Overview
TicketRecipe orchestrates the full lifecycle of a ticket-owned change from creation through completion and deprecation follow-up. It is invoked as a dedicated Temporal workflow (`ticket/{cell}/{tempTicketId}`) by the per-cell queue (`cellQueue/{cell}`) and is the canonical owner of the ticket row in Postgres. The queue grants execution rights (one active ticket per cell) and expects TicketRecipe to signal completion/rewind outcomes.

## Inputs
TicketRecipe starts without a database ticket id. Its initial inputs are supplied by the `EnqueueTicket` signal emitted by the API:
- `temp_ticket_id` (string) — stable id generated by API for this request.
- `cell` (string) — target cell for the ticket.
- `initial_metadata` (object) — actor, title, description, initial requirements/spec attachments (blob URIs).
- `resume_from_anchor` (optional) — provided during rewind, references ticket/recipe anchor from `ticket-rewind-spec.md`.
- `queue_context` — metadata echoed from the per-cell queue for logging/audit (enqueue timestamp, request id).

Internally, TicketRecipe records the canonical `ticket_id` once `ticket.manage` creates or resets the ticket.

## Outputs
- `final_summary` (markdown string).
- `git_context_patch` (map with updated hashes for parent callers).
- `deprecation_plan_uri` (string or null).
- `completion_status` (`success | blocked | rewind_requested`).

On completion, the workflow emits a `TicketCompleted` signal back to the cell queue with the outputs above plus timing metadata.

## Preconditions & Coordination
- Execution begins only after the workflow receives an `ExecutionGranted` signal from the cell queue. Until then it must remain idle but responsive to cancellation (rewind requests may arrive before grant).
- Ticket creation/update is done via `ticket.manage`; no direct DB writes.
- Rewinds arrive as `RestartFromCheckpoint` signals carrying a restart plan. TicketRecipe must honour them mid-flight (see below).

## State Machine
```
AwaitGrant -> BootstrapTicket -> Plan -> PostPlan -> ExecutePlan -> ThinpackRebase -> UpdateAgentsDoc -> Summarize -> AwaitApproval -> Finalize -> GenerateDeprecationPlan -> KickoffDeprecation -> Completed
```
A rewind can transition execution back to `ExecutePlan`, `Plan`, or other checkpointed states depending on the restart plan.

### State Details
- **AwaitGrant**
  - Wait for `ExecutionGranted` signal from cell queue.
  - If `RestartFromCheckpoint` arrives before grant, cache the restart plan and apply after grant.

- **BootstrapTicket**
  - If this is a fresh request: call `ticket.manage` with `create_ticket` using `initial_metadata`; capture resulting `ticket_id`, stage/state defaults.
  - If resuming from rewind: apply `restart_plan` instructions (`reset_ticket`, `override_markdown_doc`, attachments) before continuing.
  - Hydrate workspace (`git_shallow_clone` in shared gitstate), sync requirements docs to `.colony2/specs`.

- **Plan**
  - Invoke PlanRecipe (`recipe` op) in shared gitstate; capture `recipe_plan_uri`, spec docs, validation scores.

- **PostPlan**
  - Append plan summary via `ticket.manage` note; link plan/spec docs.
  - If human review required, pause via `input` and loop to `Plan` if edits requested.

- **ExecutePlan**
  - Interpret RecipePlan stages:
    - `recipe_set` for dependency tickets (discrete gitstates, async fan-out).
    - `recipe` for implementation phases in owning cell (shared gitstate).
  - Wait for async children, handle failure by marking ticket blocked and awaiting human input.

- **ThinpackRebase**
  - Run `thinpackrebase` to align workspace with upstream after dependency tickets complete.
  - Record rebase metadata via `ticket.manage`.

- **UpdateAgentsDoc**
  - Generate AGENTS.md summary via `llm_inference2` (Gemini Flash 2.5) and write file.

- **Summarize**
  - Produce final summary via `llm_inference2`; include tests run, major changes, dependencies.

- **AwaitApproval**
  - Request human approval with `input` op (multiple choice). On rejection, branch back to `Plan` or `ExecutePlan` per reviewer feedback; restart plan integrates new requirements as needed.

- **Finalize**
  - Execute `squashrebasemerge` (normal mode) to integrate branch; use summary as commit message (include ticket id, thinpack metadata).
  - Update ticket state to `completed` via `ticket.manage`.

- **GenerateDeprecationPlan**
  - Invoke `codex.exec` to write DeprecationPlan JSON under `.colony2/deprecations/{ticket_id}.json`; link doc to ticket.

- **KickoffDeprecation**
  - Launch DeprecationRecipe asynchronously via `recipe` op (discrete gitstate) with plan reference.

- **Completed**
  - Emit `TicketCompleted` signal to cell queue (`{status, outputs, run_id, duration}`) and close workflow.

## Rewind Handling
- Rewinds arrive as `RestartFromCheckpoint` signals containing a `restart_plan` (from `recipe-history`).
- Workflow performs the following regardless of current state:
  1. Record rewind metadata via `ticket.manage` (`reset_ticket`, notes).
  2. Cancel in-flight activities/child recipes (Temporal cancellation) and wait for cleanup.
  3. Apply restart plan instructions (restore docs, resume codex sessions, etc.).
  4. Jump state machine to the requested checkpoint (e.g., back to `ExecutePlan`).
- After rewind handling, workflow notifies cell queue via `TicketCompleted` with `status=needs_retry` so the queue can immediately re-grant execution (per queue spec).

## Error Handling
- **Plan/Impl failures**: Log via `ticket.manage`, mark ticket `blocked`, await human `input` before retry.
- **Git ops**: On `thinpackrebase`/`squashrebasemerge` failure, capture error info, request human decision.
- **Child recipe failure**: propagate to ticket notes, give operators option to rerun or abort via `input`.

## Observability
- Emit structured logs per state transition (`ticket_recipe.state`, ticket metadata, temp_ticket_id).
- Set Temporal search attributes: `cell`, `ticket_id`, `temp_ticket_id`, `plan_uri`, `current_state`.
- Metrics: state durations, number of rewinds, dependency fan-out counts, approvals requested, finalization retries.

## Implementation Notes
- Workflow must be signal-driven: `ExecutionGranted`, `RestartFromCheckpoint`, and cancellation from queue.
- Ticket creation is idempotent using `initial_metadata.request_id` to handle duplicate signals.
- Persist recipe outputs (`RecipePlan`, DeprecationPlan URIs) for inspection by other systems.
- Ensure `.colony2` directory exists before Plan/Impl phases.

## Rollout Steps
1. Implement TicketRecipe to start in `AwaitGrant`, receive metadata via signals, and create the ticket record.
2. Integrate with Plan/Impl recipes using existing DSL; handle dependency validation via helper service.
3. Wire rewind signals to restart logic, leveraging `recipe-history` restart plans.
4. Emit `TicketCompleted` signals and ensure queue restarts operate as defined.

## Open Questions
- Should plan execution be cancellable mid-flight when rewinds occur? (Current approach: yes, via cancellation on rewind.)
- How should we persist aggregated validation feedback? (Proposed: attach markdown via `ticket.manage`.)
- Do we expose additional status to queue for pausing/stealing execution (admin tooling)?
